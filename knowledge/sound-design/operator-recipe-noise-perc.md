# Operator recipe: noise-perc (hat/perc from Operator's noise waveform)

**Sourcing note:** same WebSearch-excerpt-only method as the other entries
in this batch — WebFetch was egress-blocked for every host tried this
session; citations are tied to named pages via search-tool excerpts, not
raw fetches. **All raw `device.param` values below are unverified
estimates** — read the caveat block before applying.

## Craft

**Operator has no dedicated noise oscillator** — noise is one of the five
selectable waveforms on any of its four regular oscillators (the others
being sine, square, sawtooth and triangle), per a search-aggregated
description of Operator's Wave chooser. Two Operator-specific details are
worth carrying into a percussion patch: first, "the oscillator waveform
choices are sine, sawtooth, rectangular and white noise... [the] noise
waveform is not real noise generated by a random generator, but a looping
noise sample" (an Ableton Forum thread on Operator's wave shapes) — the
noise texture is a fixed loop, not a true random generator, which matters
if a patch is layering multiple noise-waveform oscillators expecting
independent randomness; second, layering matters more than the noise
source itself: "by layering or modulating a pitched sine wave with a noise
oscillator, we can create DnB snare noises, ping-y ride cymbals, or
shimmery hihats" — a sine "ping" underneath the noise is what turns flat
white noise into something that reads as a specific piece of metal.

The core envelope principle for hats specifically, from an Operator
percussion-recipes tutorial: "the key to a good hi-hat is an interplay of
short and long decay (emulating a closed and open hat)" — i.e. this is
ONE patch, not two, with Decay/Release as the only thing that
distinguishes a closed hat from an open hat. A separate Operator-specific
walkthrough gives a concrete Operator-sourced number for the shape: "for
noise-based synthesis, change OSC A's waveform to white noise and set the
decay to 300ms and sustain to –inf dB... hi-hats use simple white noise
with minor adjustments to OSC A's ADSR" (dancemusicnw.com,
"Ableton Operator 101"). A separate pair of MusicRadar/Ableton articles on
noise-based hi-hats (built around Analog, NOT Operator — flagged since the
instrument differs) gives a shorter, closed-hat-leaning number for
contrast: "change the waveform from a sine wave to white noise, then
change the decay to 100ms, the release to 90ms and sustain to –inf dB" —
cited here only as a cross-instrument data point for how much shorter a
CLOSED hat's decay should be relative to the 300ms Operator-sourced number
above, not as an Operator fact in its own right.

## Executable

```awh-operator-patch
name: noise-perc
device: Operator
params:
  Algorithm: 0.0    # display: single-oscillator carrier shape — Osc-A alone as the only bottom-row carrier, no FM routing needed for a noise-only percussion voice. Osc-B/C/D unused/off in this base patch (see the sine-ping variant note below). Index within the 11 algorithm shapes NOT identified from sourced material — dial to the simplest single-carrier shape by eye and overwrite. RAW UNVERIFIED.
  "Osc-A Wave": 0.8    # display: Noise (looping noise sample, per the sourced Operator wave-chooser description above — NOT a true random generator). INFERRED param name (extends the A Coarse/Fine, Osc-A Level convention; the Wave chooser's device.get spelling and index-per-waveform ordering are both unconfirmed) — RAW UNVERIFIED placeholder, the 0.8 encodes only "somewhere late in a 5-item list" as a guess, not a real index mapping.
  "Osc-A Level": 1.0       # display: full noise output — RAW UNVERIFIED.
  "Ae Attack": 0.0         # display: instant — RAW UNVERIFIED placeholder.
  "Ae Decay": 0.5          # display: ~300ms, the Operator-sourced dancemusicnw number for this exact patch type ("set the decay to 300ms"). This is the OPEN-hat-leaning setting; for a CLOSED hat, shorten this toward the cross-instrument 100ms Analog reference cited above (roughly half this raw value, unverified). INFERRED param name (only Ae Attack confirmed) — RAW UNVERIFIED placeholder for how 300ms maps to raw, though the DISPLAY number itself is sourced.
  "Ae Sustain": 0.0         # display: -inf dB (silence) — sourced directly ("sustain to –inf dB") from both cited walkthroughs. Raw 0.0 is the one value in this recipe estimated with real confidence, since "-inf dB sustain" plausibly IS Operator's raw-zero floor for this parameter — still unverified by an actual readback.
  "Ae Release": 0.3         # display: short, ~90ms-ish per the cross-instrument Analog reference ("release to 90ms"), used here only as an ordering hint. INFERRED param name — RAW UNVERIFIED placeholder.
  "Filter Freq": 0.75       # display: highpass cutoff pulled well up, removing the low end noise doesn't need for a hat/perc voice (a lowpassed noise loop reads as surf/wind, not a hat). INFERRED param name, CONSTRUCTED display target (no source gives an exact Hz number) — RAW UNVERIFIED.
  "Filter Res": 0.3         # display: some resonance for a metallic "ping" character. INFERRED param name — RAW UNVERIFIED.
  "Filter Type": 0.5        # display: High-pass. INFERRED param name AND value-to-type mapping unconfirmed — RAW UNVERIFIED placeholder.
  Volume: 0.7               # confirmed device.get name. RAW UNVERIFIED for this value.
playNotes: "1|1 F#1 1 v90"
```

**Sine-ping variant (not encoded above, prose only):** per the "layering a
pitched sine wave with a noise oscillator" citation, a second oscillator
(`Osc-B`, `Waveform` sine, `Coarse` a high ratio, `Level` low, its own
envelope decaying even faster than `Ae Decay`) mixed under the noise layer
is the sourced route to a "ping-y ride" or "shimmery hihat" rather than a
flat noise hit — left as a documented extension rather than baked into the
base patch, since no source gives concrete numbers for that second layer.

## Raw values: unverified — read before applying

**CONFIRMED (not just unverified) scale bug, found via a real `awh op apply` on Operator**: `Algorithm`'s real raw range is **0-10** (11 quantized steps, `Alg. 1`-`Alg. 11`) — NOT the normalized 0-1 range this recipe assumed. Writing a 0-1-scaled value against a real device silently rounds/clamps to 0 (confirmed via read-back mismatch). Every other param in this recipe genuinely IS ~0-1 scaled. Not corrected here: knowing the real range doesn't tell us the correct index within it — still needs a real ear/UI pass.

Standing caveat (same estimation method as the other entries in this
batch): **every raw value above is an unverified estimate, not a
measurement.** No Operator raw↔display pair has ever been read back into
this repo. Apply, listen against the DISPLAY comments, correct, and record
observed raw↔display pairs back into this entry. This entry has slightly
BETTER display-value grounding than most of this batch (the 300ms decay
and -inf dB sustain are real sourced numbers, not constructions) but the
raw values that would produce them are still complete guesses — no
Operator ms→raw or dB→raw curve exists anywhere in this repo. The
`Osc-A Wave` line is the weakest link in this recipe: neither the
param's real `device.get` name nor how Operator encodes "which of 5
waveforms" as a raw float is known — probe this specifically before
trusting anything downstream of it.

## Param naming: verified vs inferred

- **Verified-style**: `Algorithm`, `Osc-A Level`, `Ae Attack`, `Volume`
  (this entry uses fewer of the fully-verified names than the others in
  this batch, since it deliberately avoids `A Coarse`/`Fine` — pitch
  ratio is meaningless for a noise waveform).
- **Inferred**: `Osc-A Wave` (weakest — see above), `Ae Decay`,
  `Ae Sustain`, `Ae Release`, `Filter Freq`, `Filter Res`, `Filter Type`.
  `awh op apply` must validate every name against a live `device.get` dump
  before writing anything, and should treat `Osc-A Wave` as the first
  thing to hand-verify in Live before trusting this recipe at all.
