# Knowledge base

The owner's deterministic production wiki (design: `docs/design/library-kb.md`).
Predefined, ACCURATE references instead of per-session re-reasoning: Claude
reads before composing, cites what it uses, and never treats a draft as fact.

## Structure

- `knowledge/<topic>/<slug>.md` — topics are **open-ended**: a new domain is
  a new directory (`setup/`, `rhythm/garage/`, `mixing/`, `projects/`, …).
  Nothing anywhere hardcodes the topic list; `awh kb index` discovers it.
- `INDEX.md` — generated by `awh kb index`; also surfaces
  `library/measurements/` records (saved mix reports are knowledge citizens:
  retrievable evidence, citable from entries).

## Entry contract

```markdown
---
slug: garage-hat-shuffle
topic: rhythm/garage        # must match the directory
tier: sourced               # verified | sourced | draft
tags: [garage, 2step]
sources: ["<url>", "own analysis of <track>"]   # required for tier: sourced
related: [library/clips/hats/rolling-garage-hats-1]
---
# Garage hat shuffle

## Executable
- pipeline: `swing:grid=0.25,amount=0.7 velocity-shape:mode=accent`
- (or an ```awh-notation``` block, an ```awh-style-spec``` block, a device recipe…)

## The rule
Prose explanation, with the numbers.
```

- **Executable-first**: whenever knowledge CAN be expressed as notation, a
  transform pipeline, a drum style spec, or a recipe, it MUST be — prose
  alone is a last resort and gets flagged `PROSE-ONLY` in the index.
- **Tiers**: `verified` (owner tested in Live) / `sourced` (distilled from
  citable references — citations required) / `draft` (proposed, untested).
  Claude states the tier whenever it applies an entry. Promotion to
  `verified` happens after real use, as an ordinary git diff.

## Executable payload types

| Fenced block | Consumed by |
|---|---|
| ```awh-notation``` | `awh lib place`-style clip writing, examples |
| ```awh-style-spec``` | `awh drums gen --style <name>` — a `drum-style-<name>` entry defines a NEW drum style as data (trap family: kick cells, hat bases, backbeat) |
| pipeline specs (inline code) | `awh vary --ops` |
| device recipes (future, B3 chain save) | `awh chain apply` |

## How entries get created

1. **Research distillation** (seeding): ask for "distill how <artist/genre>
   does <x>" → a research agent produces `sourced` entries with citations in
   a reviewable PR. Rules for agents: every claim carries its source; numbers
   over adjectives; an Executable section wherever possible; tier NEVER
   above `sourced`; one entry per rule, not essays.
2. **From the owner's own work**: `awh distill` dumps the open project
   (structure + clip notations) for curation into entries;
   "save what we learned today" at session end → `draft` entries.
3. **From measurements**: `awh mix report --save` / `awh mix target` create
   records; a knowledge entry can interpret them ("my club masters sit at
   tilt −5.2 ± 0.3 — see records X, Y").

## Retrieval (how Claude uses this)

Grep `knowledge/INDEX.md` (or `awh kb list --topic <t>`) before
genre/technique/setup tasks; `awh kb show <slug>` for the full entry; cite
`slug [tier]` when applying one. Setup facts (like `setup/sidechain-template`)
are read BEFORE designing anything that touches that part of the studio.
