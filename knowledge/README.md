# Knowledge base

The owner's deterministic production wiki (design: `docs/design/library-kb.md`).
Entries are fixed, accurate references so the same question is not re-reasoned
each time. The agent skill in `.claude/skills/awh` reads them before composing,
cites what it uses, and never treats a draft as fact.

## Structure

- `knowledge/<topic>/<slug>.md`: topics are open-ended. A new domain is a new
  directory (`setup/`, `rhythm/garage/`, `mixing/`, `projects/`, …). Nothing
  hardcodes the topic list; `awh kb index` discovers it.
- `INDEX.md`: generated by `awh kb index`. It also lists
  `library/measurements/` records (saved mix reports are retrievable evidence
  that entries can cite).

## Entry contract

```markdown
---
slug: garage-hat-shuffle
topic: rhythm/garage        # must match the directory
tier: sourced               # verified | sourced | draft
tags: [garage, 2step]
sources: ["<url>", "own analysis of <track>"]   # required for tier: sourced
related: [library/clips/hats/rolling-garage-hats-1]
---
# Garage hat shuffle

## Executable
- pipeline: `swing:grid=0.25,amount=0.7 velocity-shape:mode=accent`
- (or an ```awh-notation``` block, an ```awh-style-spec``` block, a device recipe…)

## The rule
Prose explanation, with the numbers.
```

- **Executable-first**: if knowledge can be expressed as notation, a transform
  pipeline, a drum style spec, or a recipe, it must be. Prose alone is a last
  resort and is flagged `PROSE-ONLY` in the index.
- Tiers: `verified` (owner tested in Live), `sourced` (distilled from citable
  references; citations required), `draft` (proposed, untested). The tier is
  stated whenever an entry is applied. Promotion to `verified` happens after
  real use, as an ordinary git diff.

## Executable payload types

| Fenced block | Consumed by |
|---|---|
| ```awh-notation``` | `awh lib place`-style clip writing, examples |
| ```awh-style-spec``` | `awh drums gen --style <name>`: a `drum-style-<name>` entry defines a new drum style as data (trap family: kick cells, hat bases, backbeat) |
| pipeline specs (inline code) | `awh vary --ops` |
| device recipes (future, chain save) | `awh chain apply` |

## How entries get created

1. Research distillation (seeding): "distill how <artist/genre> does <x>"
   produces `sourced` entries with citations in a reviewable PR. Rules: every
   claim carries its source; numbers over adjectives; an Executable section
   wherever possible; tier never above `sourced`; one entry per rule, not
   essays.
2. From the owner's own work: `awh distill` dumps the open project (structure
   and clip notations) for curation into entries. "Save what we learned
   today" at the end of a working session produces `draft` entries.
3. From measurements: `awh mix report --save` and `awh mix target` create
   records. An entry can interpret them ("my club masters sit at tilt
   −5.2 ± 0.3, see records X, Y").

## Retrieval

Grep `knowledge/INDEX.md` (or `awh kb list --topic <t>`) before genre,
technique or setup tasks. `awh kb show <slug>` prints the full entry. Cite
`slug [tier]` when applying one. Read setup facts (like
`setup/sidechain-template`) before designing anything that touches that part
of the studio.
